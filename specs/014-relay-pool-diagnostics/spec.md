## 1. 背景与问题

2026-09-24~25 真机排障（详见会话记录）：组网长期卡「连接中」，根因是 spec007 默认对端——社区节点 `tcp://sh.vomiku.com:7910` 停止服务（外部多点探测均 Connection refused）。排障暴露三个缺陷：

1. **单一社区节点无兜底**：社区节点本无 SLA（plan007 立项时已预警「必须多对端」），但 APP 无候选池概念，节点死了用户无从知晓、无从切换，只能人工排查。
2. **诊断只覆盖已配置对端**：现有组网诊断第③项仅 TCP 检测当前 peers，无法回答「有没有别的节点可用」。
3. **失败原因不可辨**：TCP 失败未区分 refused（服务器没监听，去服务器侧修）与 timeout（网络拦截，换网络/查防火墙），两类问题处置方向完全不同——本次排障正是靠这一区分定位根因。

## 2. 目标与非目标

### 目标（Goals）
- 组网诊断面板可对**候选中继节点池**（内置清单 + 用户自定义）逐节点做 TCP 连通检测，绿/红呈现并给出失败原因码。
- 检测完成后可**一键应用健康节点**：死节点从生效 peers 剔除、健康节点写入，走既有配置生效流水线并重启组网服务，全程无需提权、无需手改文件。
- 用户可自定义候选节点（增删、持久化），与内置清单合并检测、互不污染。

### 非目标（Non-Goals · 本期明确不做）
- 不做自动定期检测 / 自动剔除（维持「工作台只观察、动作需用户触发」的守护语义）。
- 不做 EasyTier 协议级健康探测（TCP 层判定足够；协议级需拉起探测实例，过重）。
- 不做节点延迟排名与智能选路（EasyTier 自带 `latency_first` 多 peer 择优）。
- 不涵盖 easytier-core 组件升级（本机崩溃循环问题走既有升级脚本体系，另行处理）。
- 不改动成员端（手机等）的配置形态——成员端指引沿用 007 文档。

## 3. 用户故事与验收标准

### US1: 作为远程访问用户，我希望对候选中继节点池一键体检，以便在组网异常时立刻知道哪些节点可用、坏在哪个方向

- [ ] **AC1**: Given 候选池同时含可达与不可达节点 When 用户在诊断面板点「检测中继节点」Then 逐节点显示结果：可达=绿；不可达=红并带原因码（`refused` 端口无监听 / `timeout` 网络不可达或被拦 / `invalid` URI 非法），且不因单节点失败中断整体检测
- [ ] **AC2**: Given 任一候选节点无响应 When 检测执行 Then 单节点探测超时 3s，全池并发探测，总耗时 ≤ 6s（不出现逐节点串行等待）
- [ ] **AC3**: Given 用户已添加自定义候选 When 检测执行 Then 自定义项与内置项以同一格式同列表呈现，并可区分来源（内置/自定义）

### US2: 作为远程访问用户，我希望体检后一键应用健康节点，以便不手工编辑配置文件即可完成中继切换并恢复组网

- [ ] **AC4**: Given 检测报告存在≥1 个健康节点 When 用户点「应用健康节点」Then 健康节点写入生效 peers、不可达节点剔除，`settings.json` 与渲染的 `config.toml` 保持一致，组网服务自动重启且 RPC 实况显示新对端 Connected
- [ ] **AC5**: Given 全部候选均不可达 When 用户点「应用健康节点」Then 拒绝应用并明确提示「无可用节点，已保留原配置」，原 peers 不变（防止清空 peers 导致永久「连接中」）
- [ ] **AC6**: Given 应用动作完成 When 组网状态轮询继续 Then 状态事件按新对端实况上报（在线/连接中），无需重启 APP

### US3: 作为用户，我希望维护自己的候选节点清单，以便内置清单失效时仍有自保手段

- [ ] **AC7**: Given 用户在设置区编辑自定义候选 When 提交非法 URI（缺 scheme、host 为空等）Then 行内即时红字拒绝保存，合法值才入库（对齐 007 AC11 校验口径）
- [ ] **AC8**: Given 自定义候选已保存 When 重启 APP 再进入设置 Then 清单原样保留；内置清单不因用户的增删被改写

## 4. 功能需求与边界

1. **内置候选清单**（`consts.rs` 常量，随版本更新）：初始收录经真机实测的节点——`tcp://us01.225284.xyz:11010`（2026-09-25 实测通）；保留 `tcp://sh.vomiku.com:7910`（历史默认，若复活可被检测发现）。
2. **候选池 = 内置 ∪ 自定义 ∖ 重复**（按 host:port 归一去重）；当前生效 peers 若不在池中，也纳入检测并标注「生效中」。
3. **探测语义**：复用既有 `probe_tcp`（3s 超时），新增失败原因细分（连接被拒 / 超时 / 其他 IO 错误）；探测为只读动作，不改任何配置。
4. **应用动作**：走既有配置生效流水线（密钥前置校验 → 渲染 + `--check-config` 办后校验 → 写盘 → 服务重启）；服务重启依赖 007 已授予的交互用户启停权（免提权）。应用后如新配置校验失败，保留旧配置继续服务并报错（沿用 `prepare_stack` 现行语义）。
5. **结果文案**：失败原因码走 `mesh.code.*` 双语映射惯例（固定枚举，不含用户数据/密钥）。
6. **安全约束**：候选 URI 仅接受 `tcp://`、`udp://` scheme；应用动作入参须过 011 命令面校验惯例（不信任前端传参）。

## 5. 约束与假设

- 延续 007 的多对端全连语义：peers 列表内节点同时连接，无优先级——「切换」即编辑列表（本 spec 的「应用」动作为其封装）。
- 内置清单可能过时（社区节点无 SLA），以「用户可编辑 + 检测把关」兜底，不做在线清单拉取。
- 假设组网服务 SDDL 交互用户启停权持续有效（007 T14 交付）。
