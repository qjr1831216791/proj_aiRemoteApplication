## 1. 背景与问题

新机部署本项目的三个目标（局域网访问 / 域名直连 / 域名穿透）目前需要用户跨多个入口手工操作：跑多个脚本、进 ddns-go 网页配置、手工敲 acme.sh 命令签证书、在腾讯云与 SakuraFrp 控制台之间来回切换。步骤顺序靠用户自觉，出错点全部暴露给用户（[sprint0 调研 §9.3/§9.5](../../docs/research/sprint0-cloudcli-lan-deploy.md) 的踩坑实录即为证据）。

需求方 2026-09-10 明确傻瓜式目标：**装 APP → 进向导按提示输入参数即完成**，避免复杂来回操作；必须在 web 端办理的事项给文字引导，办完后点确认并由向导校验结果。

已确认的三项决策（需求方 2026-09-10）：

1. **形态**：底层保持多个专项脚本（各自可独立运行），APP 端做装机向导串联驱动——用户面对的是一个顺序化向导，不找脚本按钮；
2. **证书**：改用带 `caddy-dns/tencentcloud` 插件的 Caddy 构建，DNS-01 签发与续期由 Caddy 自治，**acme.sh 退役**（插件调研结论：官方 caddy-dns 组织维护、v0.4.3 / 2025-11 仍活跃、CAM 凭证体系与现有 `.env`/ddns-go 一致、Caddyfile 支持 `{env.*}` 注入密钥）；
3. **范围**：三目标全覆盖——局域网在基础阶段完成即达成，直连与穿透按用户选择走分支。

## 2. 目标与非目标

### 目标（Goals）

- 新机从零到三目标任选，全程由 APP 内装机向导驱动：用户只做"输入参数 + web 端办理后点确认"，**无命令行、无手改配置文件**。
- 证书签发与每 3 个月续期由 Caddy 插件自治，acme.sh、其续期计划任务、证书文件管理从新机装机路径中消失。
- 每阶段有自动校验（密钥有效性、域名存在性、解析对齐、证书就位、隧道登录），失败给可读原因与"重试此步"，已完成阶段不受影响（断点续跑）。

### 非目标（Non-Goals · 本期明确不做）

- **不自动代办需要账户主体身份的操作**：腾讯云购域名、创建 CAM 子用户/密钥、SakuraFrp 实名与建隧道——只文字引导 + 办后校验（003"低频外部操作给入口不代劳"哲学延续）。
- **不改造旧机迁移**：向导面向新机装机；已部署旧机（acme.sh 证书链）不强制迁移、不受影响。
- **不修复网络形态本身**：CGNAT/假公网下直连不可达是网络属性，向导只如实检测与警示（004 既定口径），修复不在本期。
- **不移除专项脚本的手工可用性**：向导是编排层，脚本仍可独立运行（排障兜底）。

## 3. 用户故事与验收标准

### US1: 作为新机用户，我希望 APP 给我一条顺序化的装机向导，以便不用研究脚本和文档就能装好

- [ ] **AC1**: Given 新机已安装工作台 APP 且未完成装机 When 打开 APP Then 看板出现装机向导入口；进入向导可见阶段清单与实时检测结果（哪些已就位、哪些缺失）
- [ ] **AC2**: Given 向导部分阶段已完成 When 再次进入向导 Then 已完成阶段自动跳过（幂等），从首个缺失阶段继续

### US2: 作为新机用户，我希望基础阶段一键完成后局域网立即可用，以便最快见到可用性

- [ ] **AC3**: Given 用户在向导确认开始 When 基础阶段执行 Then 自动完成 CloudCLI 安装与防火墙放行（沿 `install-server.ps1` 语义），校验 3001 监听后向导明示"局域网访问已可用"并展示本机局域网 IP 与访问地址

### US3: 作为新机用户，我希望腾讯云侧的手工办理有逐步指引且办完即校验，以便不会配错密钥或域名

- [ ] **AC4**: Given 进入腾讯云前置（直连/穿透共用——证书 DNS-01 签发同样依赖 CAM 密钥）When 向导展示腾讯云引导 Then 分步文字指引（购域名、建子用户仅授 `QcloudDNSPodFullAccess`、建密钥）；用户经安全控制台脚本输入 SecretId/SecretKey（不回显、凭证不进 APP/IPC）后，向导完成密钥校验才放行；失败给可读原因（密钥无效/权限不足等）
- [ ] **AC5**: Given 密钥校验通过 When 用户输入域名 Then 向导校验该域名存在于该账户 DNSPod 解析列表；不存在则指引回控制台创建，不放行

### US4: 作为新机用户，我希望 HTTPS 栈（Caddy+证书）由向导代劳，以便两条通道共用一套本地终点而不接触任何配置文件

- [ ] **AC6**: Given 密钥与域名就绪 When 用户点击执行 Then 向导自动完成：下载带 tencentcloud 插件的 Caddy 落位栈目录、生成 Caddyfile（DNS-01 插件式，密钥经环境变量注入不落明文）、放行 443、启动 caddy——全程无额外用户操作
- [ ] **AC7**: Given caddy 启动 When 向导校验 Then 检测 443 已出示 Let's Encrypt 签发的有效证书（DNS-01 自动签发成功，不依赖入站 443，穿透用户同样可先取证）；失败展示 caddy 日志摘要

### US5: 作为新机用户，我希望直连分支的 ddns-go 配置由向导代劳，以便不进管理页手工配置

- [ ] **AC8**: Given 用户选择直连分支 When 执行 Then 向导生成 ddns-go.yaml（服务商/密钥/取 IP 方式/域名）并启动 ddns-go，校验权威解析 A 记录 = 本机出口公网 IP；若出口探测判定为 CGNAT/假公网则如实警示"直连大概率不可达，建议穿透通道"，不静默放行

### US6: 作为新机用户，我希望穿透通道的 SakuraFrp 办理有指引且接入自动完成，以便不读文档也能用上隧道

- [ ] **AC9**: Given 用户选择穿透通道（共用 HTTPS 栈已就绪）When 向导展示 SakuraFrp 引导 Then 文字指引（实名、创建 HTTPS 隧道·香港节点）；用户输入 access key（不回显，直写 `.env`，沿 `set-frp-key.ps1` 语义）与隧道 ID、节点域名后，向导启动 frpc 并以日志实况确认"隧道在线"；ddns-go 不被配置、不启动（通道互斥，004 语义）
- [ ] **AC10**: Given 穿透在线 When 向导进入 DNS 切换步 Then 展示腾讯云 CNAME 操作指引；用户办完点确认后向导以权威解析比对确认切换，未一致前指引不消失

### US7: 作为新机用户，我希望向导收尾即达生产态，且失败永不阻塞已完成部分

- [ ] **AC11**: Given 所选分支完成 When 向导结束 Then 提供一键注册开机自启（沿 spec 001 语义）并展示目标达成清单（局域网/直连/穿透各自状态）
- [ ] **AC12**: Given 向导任意阶段失败 When 查看向导 Then 该阶段红标 + 可读原因 + "重试此步"入口，已完成阶段状态不受影响

### US8: 作为服务端用户，我希望装机入口唯一化，以便不出现两套并行的装机路径

- [ ] **AC13**: Given 向导可用 When 查看主看板低频操作区 Then 仅剩运维工具 4 项（升级 CloudCLI / 客户端配置 / ddns-go 密码重置 / ddns-go 管理页），装机三件套与「打开工作台网页」按钮不再出现
- [ ] **AC14**: Given CloudCLI 未安装（组件卡呈引导态）When 点击组件卡上的「去安装」 Then 跳转装机向导（定位到基础阶段），而非直接拉起装机脚本

## 4. 功能需求与边界

- **向导 = APP 内编排引擎**：顺序调用既有/新增专项脚本（装 CloudCLI、装栈、生成 ddns-go.yaml、生成 Caddyfile、各类校验器），脚本保持独立可运行；APP 负责阶段编排、参数收集（不回显类经脚本控制台输入，沿 003/004 模式）、校验与结果呈现。
- **组件 × 通道矩阵**：带插件的 Caddy + 证书 = 两通道**共用**的本地终点（穿透下 TLS 在本地终结）；ddns-go = **直连专属**（穿透分支不配置、不启动，避免抢写 A 记录与 CNAME 冲突，004 互斥语义）；frpc = 穿透专属。二进制下载落位可共用，配置与启动严格按通道分支。
- **凭证安全（宪法 §3）**：SecretId/SecretKey、SakuraFrp access key 不进 APP 内存/IPC/日志、不回显输入、经脚本直写栈目录配置或 `.env`；Caddyfile 以 `{env.*}` 引用密钥，spawn 时注入，不落明文。
- **插件版 Caddy 获取**：caddyserver.com 按需构建 API 下载（版本锁定的构建参数登记 manifest）；GitHub 直连失败时沿 `install-https.ps1` 的本地 zip 兜底模式。
- **与 spec 001 的关系**：装机首配按钮（install_server / install_https / enable_https 三件套）从主看板低频操作区**移除**，向导成为唯一装机入口；「打开工作台网页」一并移除（与地址区域名行「打开」按钮同 URL，纯重复；日常入口由地址区与托盘菜单承担）。低频区保留 4 项运维工具（升级 CloudCLI、客户端配置、ddns-go 密码重置、ddns-go 管理页）并更名"运维工具"。排障兜底不靠 UI 平行入口，靠脚本本身独立可运行（文件管理器直接双击）。
- **与 spec 004 的关系**：向导的穿透分支本质是"首次配置 + 首次切换"的引导化；通道日常切换仍走 004 既有 UI，语义不变（互斥、停托管、指引检测）。
- **与 spec 005 的关系**：向导完成后日常的心跳监控归 005，向导只在装机与配置变更时刻做一次性校验。
- **DNS-01 先于入站可达**：证书签发不依赖 443 入站，直连/穿透分支均可先签证书（004 已实证该思路）。

### 4.1 向导 UI 形态

载体：**主窗口第三视图**（顶栏导航"主看板 / 装机向导 / 设置"，与既有视图切换同模式）；主看板在基础阶段未完成时顶部出现可关闭的引导 notice（完成后不再出现）。整体布局沿用看板卡片语言——左侧竖向阶段清单、右侧当前阶段面板：

```
┌────────────────────────────────────────────────────────────────┐
│ AI 远程工作台            [主看板] [装机向导•] [设置]              │
├────────────────────────────────────────────────────────────────┤
│ 装机向导        阶段状态自动保存，中断后可从缺处继续               │
│                                                                │
│ ┌─ 阶段清单 ────────┐  ┌─ 当前阶段：HTTPS 栈（共用）──────────┐  │
│ │ ① 基础      ✔完成 │  │ 说明：下载并启动 Caddy（含自动证书）  │  │
│ │ ② 腾讯云前置 ✔完成│  │ 与 ddns-go 无关，两条通道共用。       │  │
│ │ ③ HTTPS 栈 ⟳进行中│  │                                     │  │
│ │ ④ 通道分支  ○待定 │  │ 正在：下载 Caddy（带证书插件）…       │  │
│ │ ⑤ 收尾      ○锁定 │  │ [展开查看日志]                       │  │
│ │                   │  │                                     │  │
│ │ 已完成阶段可点击   │  │ ✔ 防火墙 443 已放行                  │  │
│ │ 查看详情          │  │ ⟳ 证书签发中（DNS-01，约 1~2 分钟）   │  │
│ └───────────────────┘  └─────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

交互规则（黑盒可验）：

- **阶段卡四态 chip**：待开始（灰）/ 进行中（蓝）/ 失败（红）/ 已完成（绿），复用现有 chip 色板；分支未决时④显示"待选择"、另一分支显示"已跳过"。
- **外部办理统一模式**："文字步骤 + [打开××控制台] + 办完回来点 [我已完成，开始校验]"——校验由向导自动执行，结果逐条打勾或红字给因（AC4/5/9/10 的共同交互形态）。
- **凭证输入零 APP 化**：APP 内无密钥输入框；[输入访问密钥] 拉起交互式控制台脚本（不回显、两次确认），写盘后仅回显末 4 位，UI 呈现"已配置（····1234）"徽标 + [重新输入]（宪法 §3，003/004 先例）。
- **进行中表现**：当前动作文案 + 只读可折叠日志块（等宽字体、脚本输出尾部）；阶段完成自动滚动至下一阶段并展开其面板。
- **失败表现**：失败阶段红标 + 可读原因 + [重试此步]；重试只重跑该阶段（AC12）。
- **分支选择**（阶段④）：两张单选说明卡（直连：需公网入站可达，CGNAT 可能不可用；穿透：需 SakuraFrp 账号，免公网入站），选中后展开对应分支阶段、另一分支标"已跳过"。
- **收尾表现**（阶段⑤）：目标达成清单三行（局域网/直连/穿透，各带状态点与可复制访问地址）+ [注册开机自启] + [完成，回到主看板]。
- **状态持久化**：向导会话状态由后端持有，切视图/关窗重开原样恢复（AC2 的 UI 呈现）。
- **文案**：全部双语入 i18n 词典（zh/en），沿现有 `t(key, lang)` 体系；组件级拆解（Stepper 组件、日志块复用等）在 plan.md 细化。

## 5. 约束与假设

- **架构决策**：TLS 获取方式从 acme.sh 外挂改为 Caddy 插件内置，属影响全局的选型——plan 阶段须立 [ADR](../../docs/adr/)，含回退路径。
- **回退路径**：若 caddy-dns/tencentcloud 插件停止维护或构建服务不可用，回退 B 路线（脚本包装 acme.sh）；回退只影响新机装机路径，不动旧机。
- **假设**：caddyserver.com 按需构建服务可用（当前验证中，见开放问题）；腾讯云 DNSPod API 允许程序化只读查询（解析列表/A 记录）作校验用途。
- **假设**：旧栈 `Caddyfile` 存在时不覆盖（沿 `install-https.ps1` 幂等惯例），新机一律生成插件式 Caddyfile。

## 6. 开放问题

- [ ] 插件版 Caddy 的分发方式：构建服务已验证可用（2026-09-10 实测 `caddyserver.com/api/download` 对 `os=windows&arch=amd64` + `tencentcloud@v0.4.3` 返回 HTTP 200 并正常流出二进制），但本机实测下载速度仅 ~36KB/s、二进制约 40MB——**安装时下载 vs 预构建入库随包分发**（frpc 14MB 入库有先例，Caddy 体积约 3 倍）需权衡 → plan 阶段定
- [ ] 腾讯云 API 校验的实现载体：node 子脚本（CloudCLI 装机后必有 node）vs PowerShell 原生 TC3-HMAC-SHA256 签名 → plan 阶段定
- [ ] ddns-go 取 IP 方式默认值与 CGNAT 判据（公网接口法 vs 网卡法；netInterface 模式有写入内网 IP 前科，见 004 spec §1）→ plan 阶段定
