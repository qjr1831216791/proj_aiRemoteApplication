## 3. AC11 专节：程序级规则旁路的发现与修复

**发现**（2026-09-13 验收第一轮）：需求方以同 WiFi 手机在「公用网络 + 例外关闭」组合下**仍可直访 3001**——与 AC1 预期（不可达）直接矛盾，白名单契约被判失效。

**诊断**（服务端只读取证）：`Get-NetFirewallRule` 全量盘点发现，Windows **首次运行弹窗**曾为服务进程自动创建程序级入站 Allow 规则（按 exe 放行**所有端口 × 任意 profile**）——Node.js 多条（Public/Private）、Caddy 多条、ddns-go 残留 4 条、EasyTier 全端口 Any。端口白名单契约（`CloudCLI Mesh HTTPS 443` 的 端口 443 × 源网段 × TUN 接口）被程序维度完全绕过。诊断同时证实 TUN 接口名已漂移（et_8_1999→et_8_2vfw），443 规则经重建跟踪新名（R1 实际发生且自愈）。

**契约盲区承认**：spec §1 的威胁模型与 010 白名单契约均以「端口 × 源地址 × 接口」为轴——**程序维度从未被任何轮次审查覆盖**（007 三路安全审查、010 plan 十项清单、T1~T10 实现与测试皆然）。属验收实测抓住的契约设计盲区，非实现偏差；当日回填 spec（新增 AC11 + §4 契约扩展至程序维度，见 spec §7 变更记录）后修复。

**修复**（T10，09a5917 + 19a5586）：`lan-guard.ps1` 新增 `Invoke-BypassCleanup` 并挂入 ensure-whitelist/migrate（与 TUN 解耦，休眠态也照常清理）——node 按 3001 监听进程**实际路径**精确识别（含 junction/symlink 双形态：真机 nvm 场景进程上报 `nodejs\node.exe` 而规则落库 `v23.9.0\node.exe`）、caddy 按栈目录 + 443 监听、easytier-core.exe 收紧至仅 11010 TCP/UDP、ddns-go 残留删除；误伤红线（非监听 node 版本 / wemailnode 等无关软件一律 Keep）由分类矩阵单测构造性锁定。status 契约扩展 `bypass` 五布尔（向后兼容），前端白名单行新增「旁路风险」橙警 chip；全仓 233 绿（净 +3）。

**真机前后对比**（日志 `C:\Users\Public\ac11-ensure-run.log`）：清理前 status `bypass:{node:true,caddy:true,easytierWide:true,ddnsGo:true}` 四类全真（与验收缺陷诊断一致）；第一轮清理（UAC 实跑，exit 0）**删除 10 条（node 2 + Caddy 4 + ddns-go 4）、收紧 3 处**（easytier 全端口 Any → 11010 限定双条）；清理后程序规则实况清零、easytier 栈内恰两条 11010 限定、status 五布尔全 false、`127.0.0.1:3001` 与域名均 HTTP 200、无关软件规则原样（wemailnode 8 条、其他 node 版本 10 条）；第二轮幂等复验（exit 0）五目标全跳过、「无旁路残留」。实施首战踩坑（识别函数 `return ,$out` 空结果退化为嵌套数组致删除参数为 null）当日修复并以脚本契约断言加钉。

**复测闭环**：修复后需求方最终复测——公用+无例外不可达、唯一放行组合 = 同一 WiFi + 专用网络 + 例外放行，AC11 收口。

**教训**：防火墙安全模型的审查必须**同时核验端口维度与程序维度**两类规则——按 exe 的放行面（Windows 首次运行弹窗自动创建）与端口白名单正交，单看端口契约即是盲区。本轮已把程序维度并入 lan-guard 契约与 status 常驻健康面（旁路残留 → 「旁路风险」→ 一键修复），后续安全审查轮次应将「程序级规则盘点」列为固定检查项。
