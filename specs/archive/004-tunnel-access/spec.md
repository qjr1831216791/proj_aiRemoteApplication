## 1. 背景与问题

2026-09-09 真机排查确认:宿主机长期运行在**移动蜂窝热点网络**（SSID "603"）下，其 IPv4 出口为"移动数据上网公共出口"（运营商 CGNAT），入站不可达；"移动网内路由恰好可达"不承诺、时通时断（同日实测：手机可访问 → 数小时后不可访问；海外 4 节点探测 443 全超时）。叠加既有失效模式（ddns-go `netInterface` 模式曾把内网 IP 写入公网 DNS），**DDNS 直连路线在部分网络形态下不存在稳定可达性**。

结论（需求方 2026-09-09 确认）：新增**内网穿透通道**（连接方向反转为出站，不依赖宿主机网络入站条件）作为直连的**可切换替代**。商用选 **SakuraFrp**（需求方已完成实名），**海外（非内地）节点默认**（大陆节点绑域名需 ICP 备案，延后；实际部署于 `frp-can.com`）。

两条产品约束（需求方明确）：
1. **直连方案保留**，与穿透**可切换**——不预设所有用户都能用 SakuraFrp（实名门槛/不愿用第三方/有真公网 IP 的用户继续用直连）；
2. **穿透为 opt-in**：未配置时程序行为与现状完全一致，不改变既有部署。

服务端现状：`enable-https.ps1` 装机的 HTTPS 栈 = caddy（443，acme.sh 证书）→ 上游 3001；ddns-go 维护 A 记录；工作台（spec 001）托管组件自启。另发现托管缺口：进程被杀后工作台**不自动拉起**（无守护），本 Spec 一并对新组件补齐。

## 2. 目标与非目标

### 目标（Goals）

- **双通道可切换**：主界面提供"访问通道"概念——直连（现有 DDNS 栈，默认）/ 穿透（SakuraFrp），用户显式决策切换，通道选择持久化。
- 穿透通道交付：域名 `https://ai.jackqi.cn` 经隧道公网可达，**标准 443、无自定义端口号**，不依赖宿主机网络类型。
- 隧道客户端（frpc 生态）纳入托管：随自启链按当前通道启动、**崩溃/被杀自动拉起（守护）**、收摊退出。
- 切换引导双向可用：切穿透给 DNS CNAME 指引、切直连给 DNS 恢复指引，APP 检测解析并自动消除指引（DNS 操作本体在腾讯云控制台由用户完成）。
- 主界面看板如实反映当前通道与隧道状态（在线/离线/重连中/未启用）。

### 非目标（Non-Goals · 本期明确不做）

- **不移除/不弱化直连（DDNS）方案**：ddns-go 全功能保留，直连是默认通道与回滚路径。
- **不做 APP 内自动改 DNS**：CNAME/A 记录操作在腾讯云控制台由用户完成，APP 只指引 + 检测（spec 003 哲学：低频外部操作给入口不代劳，凭证不下沉）。
- **不做 ICP 备案与大陆节点**：需求方明确延后；当前仅海外（非内地）节点。
- **不自建 VPS frp / 不做 Cloudflare Tunnel**：前者记为未来升级路径，后者国内速度实测不达标（2026-09 调研）。
- **不增加新隧道**：仅工作台 443 一条；SSH/RDP 后续按需另立。
- **不做直连模式的 DNS 诊断**：直连通道下解析是否正确由 ddns-go 自治，本 Spec 不新增检测（通道切换指引除外）。
- **不做 ddns-go 卸载**：切穿透只停止其运行与托管，文件保留以便切换回来。

## 3. 用户故事与验收标准

### US1: 作为服务端用户，我希望工作台托管隧道客户端并在看板反映其状态，以便穿透通道断链时我能直接看到原因而不是盲猜。

- [x] **AC1**: Given SakuraFrp 配置就绪（access key 经安全通道注入）且隧道已创建 When 在工作台切换到穿透通道并确认 Then 隧道客户端启动、看板通道显示"穿透/在线"，外部独立网络设备通过 `https://ai.jackqi.cn/`（标准 443）可访问。
- [x] **AC2**: Given 隧道在线 When 宿主机切换网络（WiFi ⇄ 热点）Then 隧道经自动重连恢复"在线"，期间看板如实显示"重连中"，无需人工干预。
- [x] **AC3**: Given 隧道客户端运行中 When 进程被外部杀死 Then 工作台在守护策略时限内自动重新拉起，看板状态经历"离线→在线"。
- [x] **AC4**: Given 隧道未启用或连接失败 When 看板展示 Then 显示离线/错误状态与最后一次失败原因摘要（不含 token、不打堆栈），不崩溃、不影响其他状态卡。

### US2: 作为服务端用户，我希望直连与穿透可由我显式切换，以便按自身网络条件与合规偏好选择通道，且随时可回退。

- [x] **AC5**: Given 当前为直连通道且穿透配置就绪 When 用户点击切换到穿透 Then 先展示切换说明（需要的外部操作步骤、隧道账户前提）并要求确认；确认后工作台**停止 ddns-go 托管**、启动隧道客户端，通道显示"穿透"，DNS 指引出现直至解析一致。
- [x] **AC6**: Given 当前为穿透通道 When 用户切换回直连 Then 隧道客户端停止且不被守护拉起、ddns-go 恢复托管，DNS 恢复指引（删除 CNAME、恢复 A 记录由 ddns-go 自动维护）出现直至解析一致。
- [x] **AC7**: Given 未配置穿透（无 access key 或隧道未建）When 查看通道切换入口 Then 入口呈不可用/引导态（指引去配置），**直连行为与现状完全一致**。
- [x] **AC8**: Given 通道切换完成 When 工作台重启或系统自启 Then 按持久化的通道拉起对应组件（直连 → ddns-go；穿透 → 隧道客户端），**不双拉**（两条通道组件不同时运行）。

### US3: 作为服务端用户，我希望自启与收摊语义与现有组件一致，以便通道切换不产生新的运维心智。

- [x] **AC9**: Given 开机自启已启用 When 系统启动 Then 自启链按持久化通道拉起对应组件（与现有自启同层级）。
- [x] **AC10**: Given 一键收摊 When 用户执行收摊 Then 当前通道组件与其他组件一并退出；下次启动按通道恢复。
- [x] **AC11**: Given 用户在穿透通道下停用穿透（非切换，仅停用）When 执行停用 Then 隧道客户端停止且不被守护拉起、看板显示"未启用"，通道保持穿透但标记未启用状态（或回退直连，交互形态 plan 定，确认流程含说明）。

### US4: 作为服务端用户，我希望 DNS 切换有明确指引与结果检测，以便不因解析配置遗漏导致"隧道在线但域名不通"。

- [x] **AC12**: Given 穿透通道启用且解析结果 ≠ 隧道地址（以权威 DNS 为准）When 看板展示 Then 显示 DNS 切换指引（含目标 CNAME 值与腾讯云控制台操作路径）；检测到一致后指引自动消失。
- [x] **AC13**: Given 切回直连且解析仍为 CNAME When 看板展示 Then 显示恢复指引；检测到 A 记录恢复（ddns-go 已重新写入）后指引自动消失。

### US5: 作为服务端用户，我希望在程序内配置穿透参数（隧道 ID、节点域名），以便无需手改配置文件即可启用穿透（需求方 2026-09-09 追加）。

- [x] **AC14**: Given 打开穿透设置区 When 编辑隧道 ID 与节点域名并保存 Then 配置持久化并实时影响就绪判定（校验：两项非空、隧道 ID 为纯数字）；**访问密钥不提供输入框**——仅展示 `.env` 配置指引（路径 + 变量名），凭证不进 APP/IPC（宪法 §3、003 先例）。
- [x] **AC15**: Given 设置区保存穿透配置 When 保存成功 Then 通道切换入口的就绪状态即时刷新（引导态 → 可用态），无需重启程序。
- [x] **AC16**: Given 设置区（或指引文案）提供「设置访问密钥」入口 When 用户点击 Then 拉起交互式控制台脚本（`set-frp-key.ps1`，沿 003 模式）：密钥经控制台不回显输入、两次确认后由脚本直接写入栈目录 `.env` 的 `SAKURA_FRP_KEY`——全程不进 APP 内存/IPC/日志；脚本替换既有行时保留 `.env` 其余内容，写后复核仅显示末 4 位。

## 4. 功能需求与边界

- **通道互斥语义（核心边界）**：同一时刻仅一条通道生效。根因：① `ai.jackqi.cn` 同名 CNAME 与 A 记录在 DNS 侧冲突；② ddns-go 若持续运行会与 CNAME 抢写记录。因此"穿透生效"必然蕴含"ddns-go 停止托管"，反之亦然；切换动作必须原子地完成"停旧启新 + 看板 + 指引"。
- **默认与兼容**：通道默认为直连；穿透配置项缺失时所有相关 UI/守护/自启逻辑不生效，现有部署零感知。
- **可达性口径**：穿透交付标准为"外部独立网络（非宿主机所在移动网）实测可达"，验收用真机 + 外部探测双通道（不采信宿主机本机 curl——hairpin 干扰，不构成证据）。
- **托管语义**：守护 = 周期检测进程存在，缺失则重启（退避策略 plan 定）；仅守护"当前通道应运行的组件"。自启/收摊复用 spec 001 机制，不新建平行机制。
- **token 安全**：SakuraFrp access key 属敏感凭证——存放于环境配置（`.env` 同层），禁止硬编码、禁止入库、禁止写入日志（宪法 §3）。
- **DNS 检测口径**：以权威 DNS（dnspod NS）解析结果比对目标值，公共 DNS 缓存仅作参考显示。
- **看板信息**：当前通道 + 隧道四态（在线/离线/重连中/未启用）+ 最近错误摘要；流量余量若有可用 API 则展示，无则不做（见开放问题），不为此阻塞交付。
- **证书续期约束**：切 CNAME 后 acme.sh 对 `ai.jackqi.cn` 的续期不得失效（若现用 HTTP-01 需迁 DNS-01，plan 查证后定）；直连通道下续期行为保持现状。

## 5. 约束与假设

- 依赖 SakuraFrp 服务可用性与账户免费额度（2 条隧道、10Mbps、签到流量制）；验收不承诺吞吐数字，实测显著低于宿主机上行再议节点。
- **本地网络可能拦截 frp**（2026-09-10 真机实测定案）：宿主机所在网络（家宽/公司网/公共 WiFi 的 DPI、运营商封锁）可能拦截或干扰 frp 协议，表现为 frpc 反复 `登录节点失败…EOF`、隧道迟迟不"在线"；**换网络（如手机热点）即恢复**。这是通道可用性的**外部前提**，APP 无法自愈——只能如实显示"连接中"并透出"可尝试更换网络"的建议。
- 需求方手动完成（一次性外部操作，APP 不代劳）：SakuraFrp 建隧道、腾讯云 DNS 增删 CNAME/A 记录。
- 宿主机环境假设与 spec 002 相同（使用者是管理员账户、UAC 可弹）。
- 判定逻辑（通道 × 组件状态 → 守护/自启动作、权威解析比对 → 指引显隐）为纯函数，自动化测试；GUI 走手工验收清单（宪法 §1 窄例外）。
- 假设：SakuraFrp 免费档允许绑定自定义域名（海外节点无备案要求）；若条款变化，回到开放问题重新选型。
- 假设：现有部署升级到本版本后无需任何强制配置即可继续以直连方式工作。

## 6. 开放问题

- [x] SakuraFrp 接入形态：官方启动器（GUI，不利于无头托管）vs 定制版 frpc（命令行 + token 参数化）→ plan 定，倾向后者。
- [x] HTTPS 终结位置：节点终结 TLS（证书如何提供给 SakuraFrp）vs 本地 caddy 终结 + TCP 隧道（能否保住标准 443 访问）→ plan 查官方文档后定，AC1 为准绳。
- [x] 流量余量获取：SakuraFrp 是否开放查询 API → plan 查证；无则看板不做流量展示。
- [x] acme.sh 现行续期方式（HTTP-01/DNS-01）→ plan 查证，必要时迁 DNS-01（腾讯云 DNS API）。
- [x] 守护重启退避策略（间隔/上限/告警阈值）→ plan 定。
- [x] US11 停用穿透的交互形态（保持穿透未启用态 vs 自动回退直连）→ plan 定，含确认流程。
- [x] 未来升级路径记录：自建 frp + 海外 VPS（SakuraFrp 流量制不适配长期挂机时启用）——本 Spec 不实施。
