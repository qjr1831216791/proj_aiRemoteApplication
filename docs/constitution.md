# 开发宪法（Constitution）

> 跨所有 Spec 的**不变约束**。任何 spec、plan、代码与之冲突时，以本文件为准；
> 修改本文件必须显式说明理由。所有 Spec 的 plan 阶段须对照本文件自查。

## 1. 质量底线

- **无 Spec 不编码**：新功能先有 `specs/NNN-<功能名>/spec.md` 并确认（例外见 specs/README.md）。
- **测试先行**：核心业务逻辑先写失败测试，再写实现；验收标准（AC）必须有对应测试覆盖——逻辑类 AC 须自动化测试；纯 GUI 视觉/交互类 AC 可用 tasks.md 中的手工验收清单覆盖（清单本身就是该 AC 的测试载体）。
- **回归红线**：合并前自动化测试必须全部通过，禁止跳过（skip）失败测试来"变绿"。

## 2. 工程原则

- **简单优先**（YAGNI）：先交付满足当前 AC 的最简方案，不为想象中的需求过度设计。
- **契约稳定**：对外接口（API / 数据结构 / 文件格式）变更必须记录 ADR 并更新相关 plan。
- **可追溯**：每个提交/PR 能追溯到 spec 任务编号（如 `specs/001-xxx T3`）。
- **小步交付**：一个 Spec 是可独立交付、独立验收的功能单元；过大即拆分。

## 3. 安全与合规

- 密钥、token、口令一律走 `.env` / 环境变量，禁止硬编码与提交（`.env` 已被 .gitignore 忽略）。
- 引入第三方依赖需在 plan.md 中说明用途与维护状态。
- 日志与错误信息不得泄露用户敏感数据。

## 4. 文档纪律

- 架构级决策写入 `docs/adr/`，一条决策一个文件。
- spec / plan / tasks 三文档随实现保持同步，完成时对照 tasks.md 的 DoD 检查清单收尾。
- 新建或状态变更 Spec 必须同步更新 `specs/MOC.md`。
- 用户可感知的变更必须记入 `CHANGELOG.md`（Unreleased 区）；发布新版本按其"发布步骤"执行并打 tag。
